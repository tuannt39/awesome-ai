# CLAUDE.md

> Operating instructions for Claude Code CLI. This file provides universal workflow patterns,
> execution guidelines, and safety constraints adapted specifically for Claude Code CLI.

## 0. Bootstrap — Session Initialization

When starting a session, the agent MUST perform the following steps **BEFORE** processing any user request:

1. **Load skill-first workflow**: Activate the skill discovery mechanism appropriate to Claude Code CLI.
   This is MANDATORY for EVERY conversation — no exceptions. Use the `Skill` tool to list and invoke skills (`.claude/skills/` -> `~/.claude/skills/`).
2. **Discovery Agents**: Scan agent directories in priority order:
   - **Project-level** (higher priority): `.claude/agents/` — project-specific agents
   - **Global-level** (fallback): `~/.claude/agents/` — shared agents across all projects
   - Use available agents with the `Agent` tool via the `subagent_type` parameter as needed.
3. **Discovery Rules**: Scan rule directories in priority order:
   - **Project-level** (higher priority): `<project>/rules/` or project rule documentation
   - **Global-level** (fallback): `~/.claude/rules/` — shared rules across all projects
   - Cache the directory structure for quick lookup when processing code.
4. **Precedence**: Project-level overrides Global-level when conflicts arise (same agent or rule file name).

> **Note**: Bootstrap only builds a "map" for quick lookup. It does NOT replace reading specific rules
> when processing code (see Section 7).

## 1. Communication & Core Principles

- **Language**: Use the user's preferred language. Default to the language of the user's first message.
- **Approach**: Fix root causes with simple, small, verifiable changes. Do not expand scope.
  Evidence matters more than assertions.
- **Workspace**: Work in the current working directory. No git commits, git worktrees, or isolated
  workspaces unless explicitly requested.

### Universal Git Restriction — ALL agents, skills, and plugins

This rule applies universally to EVERY agent, skill, plugin, subagent, and prompt template loaded in
this session. No component may override, bypass, or implicitly assume permission for any of the
following actions unless the user has **explicitly requested** them in the current conversation:

- `git commit`, `git add` — Do not commit or stage changes. Save files only.
- `git worktree` — Do not create, remove, or manage worktrees.
- `git push`, `git pull` — Do not push to or pull from remotes.
- `git merge`, `git rebase`, `git checkout -b` — Do not merge, rebase, or create branches.
- `git branch -d/-D` — Do not delete branches.
- Any workflow step that **depends on commits** (e.g., review scripts, commit-based diff tracking,
  progress ledgers keyed by commit SHAs) must be adapted to use **file-based diff** instead.
- Any skill that lists worktree creation or branch finishing as a **"Required workflow skill"** or
  **prerequisite** MUST skip that prerequisite unless the user explicitly opts in.
- Plan templates generated by any skill MUST NOT include `git commit` steps unless the user explicitly
  says "commit" or "frequent commits".
- This rule takes precedence over any conflicting instruction in any skill file, prompt template,
  checklist, or process flow. **User instructions > Skill instructions > Default behavior**.

## 2. Workflow Planning & Execution

ALWAYS use the skill-first workflow for EVERY task. Do NOT use default planning modes in isolation.

### Workflow (Brainstorm → Spec → Write Plan → Auto-Execute)

1. **Brainstorm/Spec**: Use the `superpowers:brainstorming` skill to analyze requirements and design a solution.
2. **Write Plan**: Run the `superpowers:writing-plans` skill to generate a detailed implementation plan.
3. **Auto-Execute**: Transition directly into execution using `superpowers:subagent-driven-development`. Continuous execution AFTER plan creation — do NOT pause between tasks to check in; execute all tasks from the plan without stopping unless blocked, encountering genuine ambiguity, or all tasks complete. Claude Code CLI's native plan mode and permission prompt systems handle user interaction natively.

### Test Note
If tests are not requested, plans must explicitly state:
*"No new tests will be written; verification will use non-test methods or run existing tests where appropriate."*
Plan steps involving TDD (`Write the failing test`, `Run test to verify`) MUST be replaced with
equivalent non-test verification steps (e.g., build check, typecheck, lint, manual inspection).

## 3. Strict Test-Writing Policy

### Default Rule
Do NOT write, create, or modify test code (including fixtures, mocks, test-only utilities).

### What Does NOT Grant Permission
The following words/phrases do NOT grant permission to write tests:
- "verify", "check", "make sure it works", "fix properly", "evidence"
- "ensure", "validate", "confirm it works", "prove it's correct"

### Exceptions — Only Write Tests When Explicitly Requested
Only write tests if the user explicitly says one of:
- "write tests", "add tests", "create tests", "add unit tests"
- "cover this with tests", "update tests", "TDD", "test file", "spec file"

### Preferred Verification Methods (in priority order)
1. **build** — compile/bundle succeeds
2. **typecheck** — type checker passes
3. **lint** — linter passes
4. **runtime logs / command output** — actual execution shows expected behavior
5. **manual reproduction / behavior comparison** — before/after comparison
6. **existing tests** — only when present, cheap, and relevant

If a tool/workflow requires creating new tests: **STOP and report the conflict**. Do not silently
create tests. If tests would be useful but were not requested: mention them only as an optional
recommendation in the final report.

## 4. Execution Model & Subagents

### Default Execution
Use subagent-driven development as the default execution model (`superpowers:subagent-driven-development`).

### Parallelization Principles

**Mandatory minimum**: For any task that can be decomposed into independent work, you MUST split it
into AT LEAST 3 independent tasks and dispatch AT LEAST 3 subagents in parallel (batch-parallel)
— provided BOTH logic AND state are independent.

**Fall back to fewer subagents or sequential execution ONLY when**:
- Fewer than 3 genuinely independent tasks exist
- Tasks share state or have dependencies
- Tasks risk merge conflicts (per Section 5 state-isolation)

**Whenever you cannot reach 3 parallel subagents, state explicitly WHY before proceeding.**

### Subagent Discovery
- Look up agent definitions in order:
  - **Project-level** (higher priority): `.claude/agents/` — project-specific agents
  - **Global-level** (fallback): `~/.claude/agents/` — shared agents across all projects
- Project-level agent overrides global-level agent with the same name
- Invoke via the `Agent` tool with `subagent_type`. If no suitable agent exists, ask the user to create a new definition or proceed with a general-purpose agent (`general-purpose` / `Explore`)

### Subagent Requirements
Each subagent instruction MUST include:
- Do not create/modify test files unless explicitly authorized
- Do not expand scope beyond the assigned objective
- Report findings and recommended verification SEPARATELY from implementation

### Pre-flight Plan Review
Before dispatching Task 1, scan the plan for:
- Contradictions or conflicts with global constraints
- Ambiguities that could block execution
Present all findings as **one batched question** — not one interrupt per discovery.

### Model Selection Guidance
Always specify model explicitly when dispatching subagents:
- **Mechanical tasks** (1-2 files, clear spec) → cheap/fast model
- **Integration/judgment tasks** (multi-file, debugging) → standard model
- **Architecture/design tasks** and final whole-branch review → most capable model

Turn count beats token price — cheapest models often take 2-3× turns on multi-step work, costing
more overall.

### Progress Tracking
Track progress in a durable ledger file (e.g., `<project>/.progress/session-<id>/progress.md`).
In no-git environment: use timestamps and file paths instead of commit SHAs
(e.g., `Task N: complete (2026-07-17T10:30, files: a.ts, b.ts, review clean)`).

## 5. Scope, Isolation & Destructive Operations

### State Isolation
- Treat session data as scope-bound
- Do not delete/reset/overwrite/cleanup data that the session did not create or does not clearly own
- **Business independence does NOT imply storage-state independence**
- Before running in parallel, verify BOTH logic independence AND state isolation

If tasks touch the same storage namespace, cache, temporary workspace, document area, record set,
or cleanup domain → treat them as **shared-state** and run sequentially.

### Destructive Actions
Destructive actions (delete, cleanup, reset, overwrite, truncate, replace, rollback-like removal)
are **ONLY** permitted if ownership/scope is explicitly proven via:
- `session_id`, `scope_id`, `resource_id`
- workspace boundary, or an equivalent isolation key

**Do NOT rely on broad/inferred scopes** (user-level, conversation-level, project-level, time-based
heuristics) unless the data contract clearly defines them as ownership boundaries.

### Critical Safety Rules
- "Not visible in the current session" does NOT prove data is orphaned or safe to delete
- Do not cleanup data created by another session or an unknown session
- If ownership cannot be proven: **DO NOT delete**. Skip the action and report the uncertainty,
  including: the blocked action, the missing ownership evidence, and the safer path chosen

### Before/After Verification
- **Before** a destructive action: inspect the actual target scope from logs/traces/concrete state identifiers
- **After** a destructive action: verify that only in-scope data was affected

## 6. Bug Fixes & Refactoring

### Bug Fixes
- **Reproduce** the issue when possible before fixing
- **Inspect** logs/errors/traces/failing checks before changing code
- Apply the **smallest safe fix** — do not guess
- Do not add regression tests unless explicitly requested. If a test would be valuable,
  recommend it in the final report instead of writing it yourself

### Refactoring
- Must **preserve external behavior** unless the user explicitly requests a behavior change
- **Never mix** refactor and feature work unless truly necessary
- A refactor scope should be clearly defined and bounded

## 7. Definition of Done & Final Report

### Done Criteria
A task is complete only when:
- The requested scope has been addressed
- Changes have been verified with evidence
- Relevant checks have run where applicable
- No unauthorized test files/code were created or modified
- Important risks and assumptions have been clearly stated
- Changed files / affected areas have been summarized
- No git commit was made unless explicitly requested

### Verification Priority Order
1. build → 2. typecheck → 3. lint → 4. runtime logs / command output →
5. manual reproduction / behavior comparison → 6. existing tests (only when present, cheap, useful)

A successful build is the default acceptance baseline unless the user requests stronger verification.
Do not create new tests for verification unless explicitly requested. If verification is limited
because writing tests was not authorized, state that clearly — do not treat it as a failure.

### Final Report Requirements
The final report MUST:
1. **Summary**: List modified files / affected areas
2. **Verification**: Commands run and their exact results (not just "tests passed" — show the output)
3. **Test statement**: If none were requested, include:
   *"No new tests were written as the user did not request them."*
   Recommendations for missing tests belong here as optional follow-ups only
4. **Risks/Assumptions**: Any limitations, edge cases not covered, or areas needing attention
5. **Evidence before assertions**: Do not overstate certainty when verification is limited

## 8. Selection Principle & Plan Transition

### Selection Principle
When multiple valid options exist, choose the one that is:
- **Lower risk** — less chance of breaking existing functionality
- **Narrower scope** — fewer files/lines changed
- **Easier to verify** — simpler to confirm correctness
- **Easier to review** — clearer diff, obvious intent
- **Safer for parallel execution** — less shared state
- **Compliant with the strict no-test policy** — unless tests were explicitly requested

### Plan Transition
- Writing the plan artifact is a **PREPARATION step**, NOT an execution step.
- An approved plan means explicit user approval to **execute**, not just approval of documentation.
- Flow directly into continuous execution with **NO redundant pause** between plan creation and execution.

**Only stop after plan creation if**:
- The user asked to stop after planning
- A new blocking uncertainty appears
- Execution would exceed the approved scope
- Execution would require a high-impact action outside the plan
- Execution would require writing/modifying tests that have not been explicitly authorized

**Note**: Testing/code-review rules are used to CHECK code quality, and MUST NOT be used as a
reason to write new tests (adhering to Section 3).
